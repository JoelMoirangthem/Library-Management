# StudySeat — Decisions

Newest at the bottom. Each entry: decision, reason.

- **D-001 No custom backend.** React as a static site (Render, see D-034) + Supabase. The database enforces all rules via RLS and functions, so a modified browser cannot cheat.
- **D-002 Manual UPI for the ₹199 plan.** Owner submits UTR, admin verifies. A gateway later needs an Edge Function and webhook.
- **D-003 Single `active_until` column.** `trial_ends_at` is kept for display only. Rules check `active_until`. Payments extend from `greatest(now(), active_until)`.
- **D-004 Trial starts on first approval only.** Re-approval never resets it.
- **D-005 Expired = read-only.** All owner writes blocked except `submit_plan_payment`. Nothing is deleted.
- **D-006 Role set once via `set_my_role`.** Column grants block client updates to `profiles.role`. Admin only via SQL.
- **D-007 One library per owner in v1.** `unique (owner_id)`.
- **D-008 Derived, not stored.** Seat occupancy from active members; member expired/due from `expiry_date` in Asia/Kolkata. No `fee_status` column.
- **D-009 Expired members keep their seat** until the owner removes them or frees the seat.
- **D-010 No partial fee payments in v1.** A renewal is one payment and one expiry extension.
- **D-011 Multi-row actions are SQL functions** (`approve_seat_request`, `renew_member`, `set_capacity`) so they succeed or fail as a whole.
- **D-012 Money in integer paise; no hard deletes** on money or membership records.
- **D-013 SOLID with plain TypeScript.** Pages → Hooks → Services → Repository interfaces; Supabase code only in `repositories/supabase` and `lib/supabase.ts`; wiring in `lib/container.ts`. No DI library.
- **D-014 RLS tested by impersonation**, because the SQL editor bypasses RLS.

- **D-015 Light mode only in v1.** Components use semantic tokens (`bg-surface`, `text-ink-muted`), never raw hex, so dark mode stays possible. The default Tailwind palette is disabled in `src/index.css` so raw colours fail loudly.
- **D-016 Palette chosen by measured contrast.** Primary teal `#0F766E` (5.47:1 on white; the common `#0D9488` is 3.74:1 and fails). Accent orange `#C2410C` (5.18:1; `#EA580C` is 3.56:1). Orange is used rarely: Activate plan, trial ending. Form control edges use `border-strong` (`#78716C`, 4.8:1) because decorative `border` (`#E7E5E4`) is below the 3:1 needed for controls.
- **D-017 One font: Inter, self-hosted** via `@fontsource-variable/inter` (no Google Fonts request). Verified in the font file: `tnum` exists and digits 1 and 8 are both 1328 units wide when enabled. Apply `tabular-nums` on tables, prices, seat numbers, and stats, not on the whole body. The ₹ glyph lives in the latin-ext subset, which the browser loads on demand.
- **D-018 Seat state is never colour alone.** Each state has a second cue (fill shape, ring, clock dot, hatching). Seats are real `<button>`s with descriptive labels. Detailed in the SeatGrid component when built.
- **D-019 Non-happy-path screens share one component set:** `LoadingState`, `EmptyState`, `ErrorState` (retry), `NotFoundState`, `SetupState`, all built on `StateShell`. Error means "retry may work"; not found means "does not exist".
- **D-020 `/dev/styleguide` is development-only.** It sits behind `import.meta.env.DEV`; the production build contains neither the route nor its code (checked by searching `dist/`).

- **D-021 Dummy-first.** The whole UI runs on mock repositories (in-memory, saved to localStorage) that implement the same interfaces as the future Supabase ones. `VITE_DATA_MODE=mock` is the default. The mock enforces the same rules as the SQL (see `src/repositories/mock/mockRules.test.ts`), but it cannot prove security: Row Level Security must still be tested against real Supabase with two real accounts.
- **D-022 All time comes from one place.** Pure rule functions take `now`/`today` as parameters; the app asks `getNow()` / `useNow()` (`src/lib/devState.ts`), which the Demo panel can shift. No business logic calls `new Date()` directly.
- **D-023 A mock write bumps a data-version counter** so every mounted query refetches; pages rarely refetch by hand.
- **D-024 Seat cells are built in one place** (`src/domain/seatCells.ts`), so the grid, dashboard and student list can never disagree.
- **D-025 Shifts (3 max, no overlap, own fee each).** A seat is free or taken per shift (`unique (seat_id, shift_id)` for active members). Each library starts with Morning / Afternoon / Evening defaults. Shifts are never deleted, only switched off; their students stay tagged. One person in two shifts = two memberships. Library-wide `monthly_fee` is removed; the library list shows `from` the lowest shift fee.
- **D-026 Real backend is Supabase, reached only through repositories.** `VITE_DATA_MODE=supabase` swaps the mock repositories for `src/repositories/supabase/*`; pages and rules do not change. Schema, RLS and every write that must be atomic or privileged live in `supabase/migrations` (0001 to 0011). Sign-in is Google OAuth with PKCE. The browser only ever holds the public anon key; the `service_role` key is never used. Money and membership rows are never hard-deleted (a trigger forbids it); fees are voided with a reason.
- **D-027 Plan renewal rule (owner's decision, 18 Oct 2026).** Paid in advance: the days left stay and 30 stack on top (3 left becomes 33), even if the admin verifies late. Paid after expiry: 30 days from the day the admin verifies. Implemented in `verify_plan_payment` (migration 0009) and mirrored by `extendedActiveUntil` for the mock and the preview text; the same cases are tested in both.
- **D-028 Real writes refresh the screen.** The mock bumps `dataVersion` on every save; real repositories are wrapped by `refreshAfterWrites` so any non-read method (not `get`/`list`/`search`) bumps it after it succeeds. A failed write does not.
- **D-029 Photos are files in Supabase Storage, not text in the library row.** Public bucket `LibraryImages`, one flat folder per owner (`<owner id>/<random>.jpg`). Migration 0010 lets only an owner upload into their own folder (JPEG/PNG, 5 MB, 20 files) and list/delete their own; anyone can view by link. `libraries.photos` holds at most 4 links into the owner's own folder (a check constraint rejects data: blobs, other sites and other owners' files). The picker shrinks to a JPEG, uploads on pick, and keeps only the link; a library save deletes every file no longer in use, so abandoned uploads cannot fill the 20-file cap. Dummy mode keeps data links in the browser. File names are random and never reused, so a cached old link can never show the wrong photo (a deleted file can still be served from Supabase's CDN cache for a short while).
- **D-030 A production build defaults to the real backend.** `resolveDataMode`: an explicit `mock` or `supabase` wins; if the setting is missing, development uses dummy data and production uses Supabase. A forgotten setting on the host can therefore never ship fake data or the demo panel. The public footer says "Demo data only." in dummy mode only.
- **D-031 Strict security headers.** (First set in vercel.json; now in render.yaml, see D-034.) Scripts only from the site itself; images, API and websockets only to `https://*.supabase.co`; no framing; nosniff; HSTS. Chosen because the production bundle has no inline scripts and the app talks to no other host. Verified with the real headers applied to the production build across owner, student and admin screens (0 violations).
- **D-032 Lists are read page by page.** The Supabase API returns at most 1000 rows per request however many are asked for (measured on this project: a request for rows 0 to 9999 returns 1000). `fetchAll` in `src/repositories/supabase/paging.ts` reads fees, members, payments, requests and the admin lists 1000 at a time with a unique sort order, and `chunk` sends student ids in groups of 100 so the web address stays short. Proven with 1250 students, 2300 fees, 1100 payments and 1150 requests on the real project. Known limit: the public Discover search (`public_libraries`) is a single call and would stop at 1000 libraries; far above the pilot, to be paged when it matters.
- **D-033 A missing Supabase setting shows a readable screen.** Startup code only touches Supabase when the URL and key are present (`hasSupabaseConfig`), so a deploy without them shows "StudySeat isn't set up yet" and names the missing variables instead of a blank page. Migration 0011 pins `search_path` on the helper, trigger and constraint functions; it deliberately does not revoke EXECUTE on them, because the shift trigger and the photo check constraint run as the signed-in owner and need it.
- **D-034 Hosting is Render (static site), configured by `render.yaml`; this replaces `vercel.json` (D-031).** The same security headers and single-page-app rewrite now live in the Blueprint, which was validated against Render's published schema. `vercel.json` was removed so there is one source of truth. Verified from a clean copy of the repository (no `.env`, no `node_modules`): `npm ci` and `npm run build` succeed, and a brand-new owner and student can run the whole business loop against the production build with the Blueprint's headers applied (0 policy violations, 0 console errors).
- **D-035 The database password lives in `.env`, read by `npm run db:push` / `db:query`.** `SUPABASE_DB_PASSWORD` is plain text; `scripts/dbUrl.mjs` builds the pooler address and percent-encodes it (an `@` or `#` in a password broke hand-built addresses before). The variable names do not start with `VITE_`, so Vite never copies them into the website; checked by building with a canary value and finding it in 0 of the files in `dist`. Tool output has the password masked. The website itself never uses it.
- **D-036 The Discover search is read page by page too** (`public_libraries` through `fetchAll` with a fixed order). Function calls page with `limit`/`offset` in the web address; the `Range` header is ignored for them (measured). Proven with 1101 public libraries: the old single call returned 1000. This closes the limit noted in D-032.
- **D-037 Admin screens ask for only what they show.** Owner names and library names are looked up for the rows on screen (`fetchByIds`, groups of 100), and the menu badges use count-only requests. `count*` methods count as reads in `refreshAfterWrites`: a count treated as a save reloaded the screen in an endless loop (16,000 requests in 30 seconds, caught before release).
- **D-038 CI on GitHub.** `.github/workflows/ci.yml` runs the type check, lint, tests and a production build on every pull request and every push to `main`, on Linux (which also catches file-name capitalisation mistakes that Windows hides).
- **D-039 Libraries are split from app code.** React with the router, and the Supabase client, are their own files (`vite.config.ts`, `codeSplitting.groups`). After a code change only the 100 kB app file changes name, so returning visitors keep about 470 kB cached.
- **D-040 New tables start closed (migration 0012) and the live rules are checked by a script.** Supabase hands the web roles full access to every table created later in `public`; 0012 removes that default for tables and sequences (tested: a careless new table was readable by the public before, not after). Functions are NOT covered by this: Postgres lets everyone run a new function through its built-in PUBLIC group, so every migration must keep revoking from `public, anon, authenticated`. `npm run security:check` (`scripts/securityCheck.mjs`, rules in `securityRules.mjs`, unit-tested) fails if any function outside an approved list is runnable by strangers. Proven able to fail: three deliberate breakages (table without row security, open function, writable role) were each detected inside a rolled-back transaction.
- **D-041 Attacker tests are kept out of the repository.** A scripted run of about 130 attacks and 6 race tests with real accounts (two rival owners, students, admin, a role-less user, forged tokens) left the database byte-for-byte unchanged and the races produced exactly one winner each. The script is not committed because it needs accounts with a known password, including an admin; run it from a private copy against a throwaway or staging project.
- **D-042 Extra response header.** `X-Frame-Options: DENY` is added next to `frame-ancestors 'none'` for old browsers. HSTS stays `max-age=31536000` without `preload`/`includeSubDomains`: preload is close to irreversible and the site starts on an `onrender.com` address; revisit with a custom domain.
- **D-043 The administrator signs in with a user ID and password at `/admin-login`; everyone else uses Google only.** The ID maps to `<id>@admin.studyseat.invalid` (`src/domain/adminLogin.ts`); `.invalid` is reserved and cannot receive mail, so no outside party can reset or intercept it and no Google account can collide with it. The Email provider has to be on for this, so registration is closed at the database instead: migration 0013's trigger on `auth.users` refuses any email-provider user unless `studyseat.allow_email_user` is set in the same transaction, which only `npm run admin:set-password` does. After password sign-in the app loads the profile and signs out again unless `role = 'admin'`; every failure shows the same message. The account is created locally by a tool that hides the typed password, enforces a strong one (14+ characters, mixed classes, no easy words or years, not the user ID) and has the database make the bcrypt hash. A password given in chat was deliberately not used. A first version of the SQL builder wrapped the statement in a fixed `$$` delimiter, so a password containing `$$` could end it early; the unit tests missed it and a run against the real database caught it. The wrapper tag is now random and redrawn until absent from every value, and the final statement was verified on the live project (rolled back) with a hostile password: its hash verifies that exact password and a wrong one fails, and running it twice leaves one account. `security:check` gained two rules (guard installed; no email accounts outside the admin domain).
